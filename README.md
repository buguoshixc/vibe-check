# vibe-check

中文 | [English](README.en.md)

> 面向不懂编程的同学的"AI 代码质检员"：vibe coding 时替你**独立评审** AI 写的代码和提的方案，用大白话告诉你"能不能用、有什么坑、下一步怎么办"。

遵循开放的 **Agent Skills** 格式（`SKILL.md`），适用于支持该格式的主流 AI 编程助手——Claude Code、Qoder CLI、GitHub Copilot（agent 模式）等，**不绑定单一产品**。

## 它解决什么问题

不懂编程的人用 AI 写代码（vibe coding）时，有一个绕不开的困境：

**同一个 AI 既写代码，又评价代码。** 它说"已经测试过了，功能完整"，你没法验证；它给出三四个技术方案让你选，你看不懂区别；它写了一堆代码，你不知道里面有没有坑。结果就是——你只能选择"相信它"，而它常常过度自信。

vibe-check 就是来打破这个困境的。它扮演两个角色：

1. **独立评审员**：站在"找问题"而不是"护短"的立场，**实际运行代码拿证据**，不轻信 AI 的自述，给你明确的"能不能用"结论。
2. **大白话翻译官**：把专业术语翻译成生活比方，把技术利弊翻译成你能懂的维度（花不花钱、会不会被绑死、搞砸了能不能退回），让你**有能力做判断**。

它不替你写代码，而是帮你**看懂和把关** AI 写的代码与方案。

## 快速开始

```bash
git clone https://github.com/buguoshixc/vibe-check.git
mkdir -p ~/.claude/skills          # 按你的产品替换目录，见下文安装表
cp -r vibe-check/vibe-check ~/.claude/skills/
```

重启会话后，对 AI 的产出问一句"这样行吗？"或输入 `/vibe-check`，它就会开始评审。

## 核心功能

### 1. 独立评审员

- **评代码**：读改动 → 实际运行（跑脚本／起服务器／跑测试）→ 按 7 项清单逐项找证据 → 给结论。
- **评方案**：核对方案与你的真实目标（课程作业？自己用？给别人用？）是否匹配，检查有没有过度设计，按五维度对比利弊。
- **对抗式独立评审**：改动较大或涉及删数据、密钥、付费时，派一个**全新上下文的子代理**重新审一遍，避免"自己给自己打分"。
- **红绿灯结论**：🟢 放心用 / 🟡 有隐患 / 🔴 建议返工，一句话说明理由。
- **可复制的修复指令**：直接生成一段能发给编码 AI 的话，具体到文件和行为，你不用自己组织语言。

### 2. 大白话翻译官（触发后整个会话生效）

- 术语第一次出现必须打比方（API＝服务员、数据库＝账本、回滚＝后悔药……）。
- 给方案时**给一个明确推荐＋各方案利弊表**，而不是丢一堆选项让你自己选。
- 评审报告正文 ≤400 字，先说结论，细节你问了再展开——不拿一墙字吓你。
- 语言跟随你（中文问就中文答）。

## 工作原理

评审分四步，前两步是硬性的：

```
① 判定评审对象 → ② 收集证据（实际运行） → ③ 大改动派独立子代理 → ④ 按固定模板输出
```

**① 判定评审对象**：你指定了就评指定的；没指定就看最近对话——刚写完代码评代码，刚提了方案评方案。纯概念提问（"X 是什么"）只用大白话解释，不走评审。

**② 收集证据（不可跳）**：脚本用正常输入和边界输入各跑一遍；网页起本地服务器确认能打开、再核对关键行为；有测试就跑测试。**跑不了就明说"未实际运行，仅基于阅读"，并把结论降一档。** 会花钱、删数据、对外发请求的操作先问你。

**③ 大改动派独立子代理**：超过约 100 行／跨多文件／涉删数据、密钥、付费时，派全新上下文子代理找茬，**不给它看先前的结论或 AI 的自述**。小改动自审省成本。

**④ 固定模板输出**：红绿灯 → 问题列表（≤5 条，按严重度排）→ 方案对比表（评方案时）→ 可复制修复指令 → 证据脚注（跑了什么、没验证什么）。

### 红绿灯判据

| 结论 | 评代码 | 评方案 |
|---|---|---|
| 🟢 放心用 | 验证过，且无高／中严重度问题 | 匹配目标、无高风险、代价已说清 |
| 🟡 有隐患 | 有隐患但能用，或部分未验证 | 方向对，但有代价要防 |
| 🔴 建议返工 | 会丢数据／泄露／崩溃，或没做到你要的事 | 方向性错误（严重过度设计／危险操作） |

**拿不准时宁🟡不🟢。**

### 诚实原则

- 运行结果只写亲眼看到的，不编造。
- 没验证的部分明确标注，不把不确定说成确定。
- 评审不通过不替作者找借口，但修复指令具体可执行，不只说"重写"。

## 输出长什么样

**代码评审示例**（一个"声称已测试、接了云同步"的待办网页，实测后）：

```
🔴 建议返工
核心问题：待办一刷新就全没，"云端同步"也是空壳——声称的功能没兑现。

发现的问题（按严重度排）
1. 待办只记在"脑子"里没写进"本子"：一刷新就全忘，像写在沙滩上（高）
2. "云端同步"是假的：实测一次联网都没有，说法不实（中）
3. 钥匙贴在门上：密钥写死在网页里，换真钥匙谁都能拿走（中）
...

下一步（可直接复制发给写代码的 AI）
> 修改 todo.html：todos 用 localStorage 持久化；删除未使用的密钥；
> 渲染用 textContent 禁止 innerHTML 拼输入；拦截空输入；自测刷新不丢。

---
证据：服务器实测 HTTP 200；模拟实测刷新后列表清空、联网 0 次。
没验证：无真实浏览器，点击体验未测。
```

**方案对比示例**（"React＋数据库 vs 单文件 HTML 做记账页面"）：见[五个维度](#方案对比的五个维度)下方的表格示例。

## 方案对比的五个维度

不堆术语，只问你真正关心的事：

| 维度 | 大白话 | 自查问题 |
|---|---|---|
| 成本 | 花不花钱、花多少时间 | 要买服务器／付费服务吗？搭起来要多久？（学生预算默认≈0） |
| 依赖轻重 | 要装多少别的东西、会不会被绑死 | 装几个包？以后想换方案要重写多少？ |
| 能否回滚 | 搞砸了能不能退回 | 有存档吗？这步会删数据／花钱吗？ |
| 维护难度 | 以后改一个小功能要动几处 | 你自己看得懂、改得动吗？ |
| 风险 | 最坏会发生什么 | 丢数据？泄露？白干一周？概率多大？ |

对比表示例（个人自用记账页面）：

| | 方案A：React＋数据库 | 方案B：单文件 HTML |
|---|---|---|
| 成本 | 租服务器花钱，搭建数天 | 0 元，几分钟能用 |
| 依赖轻重 | 装三大件，换方案得重写 | 不装零件，双击就开 |
| 能否回滚 | 环节多，难退回 | 复制文件即存档 |
| 维护难度 | 改一处动三处，你修不动 | 一个文件，AI 能帮改 |
| 风险 | 白花钱白干，坏了没人修 | 清浏览器丢账，备份可防 |

> 我推荐 B。对你最要紧的是自用、零预算、不会编程，B 这点全占。A 的好处是扛多人用、存大量数据，但代价是持续花钱和你搞不定的维护。

## 安装

把 `vibe-check` 文件夹放进你所用产品的 skills 目录即可。常见位置：

| 产品 | 项目级（仅当前项目） | 用户级（所有项目） |
|---|---|---|
| Claude Code | `.claude/skills/` | `~/.claude/skills/` |
| Qoder CLI | `.qoder/skills/` | `~/.qoder-cn/skills/`（国际版 `~/.qoder/skills/`） |
| GitHub Copilot（agent 模式） | `.github/skills/` 或 `.claude/skills/` | `~/.copilot/skills/` |
| 其他支持 Agent Skills 的产品 | 各自的 skills 目录 | 同左 |

**分步安装（以 Claude Code 用户级为例）：**

```bash
# 1. 克隆仓库
git clone https://github.com/buguoshixc/vibe-check.git
cd vibe-check

# 2. 复制到 skills 目录（Qoder 换成 ~/.qoder-cn/skills）
mkdir -p ~/.claude/skills
cp -r vibe-check ~/.claude/skills/

# 3. 重启会话；Qoder 可执行 /skills reload
```

**验证**：在产品的技能列表里确认出现 `vibe-check`（Qoder 用 `/skills list`）。装好后它会在你表达疑虑时自动触发，也可手动 `/vibe-check`。

> 项目级 vs 用户级：想让所有项目都能用就装用户级；只想在某个项目里用就装项目级（放进该项目根目录的对应文件夹）。

## 用法

**手动调用**：输入 `/vibe-check`。

- 留空：自动评审最近的代码／方案。
- 带对象：`/vibe-check 这段代码` 或 `/vibe-check 该选哪个方案`，评你指定的内容。
- 多数产品支持斜杠调用技能；不支持的话，直接在对话里点名"用 vibe-check 帮我看看"也行。

**自动触发**：当你对 AI 产出表达疑虑时自动启用，例如：

- "这样行吗？" / "靠谱吗？" / "会不会翻车？"
- "帮我看看有没有问题" / "这代码质量怎么样"
- "该选哪个？" / "这两个方案有什么区别"

**触发后**：大白话沟通规则在整个会话持续生效；深度评审按需进行，不会每句话都走完整流程。

## 设计原则

- **证据优先于声称**：AI 说"已测试"不算数，运行结果才算。没跑就下结论是头号违规。
- **独立于作者**：评审立场是找问题，不是护短；大改动用全新上下文子代理，避免自我背书。
- **大白话优先于术语**：用户看不懂术语，等于什么都没说。
- **给判断而非给选项**：明确推荐＋利弊，而不是把选择难题丢回给不会选的人。
- **诚实降级**：验证不了就明说，并降低结论置信度，绝不把不确定包装成确定。

## 兼容性与限制

**需要的能力**（都是通用能力，不依赖特定产品）：

- 读文件、用 shell 运行代码（取证）。
- （可选）派独立子代理。没有子代理能力的产品会**自动降级为自审**，并在报告里注明"未派独立评审"。

**已知限制**：

- 无真实浏览器时，网页只能验证"能打开＋逻辑核对"，点击体验／外观会标注"未验证"。
- 独立子代理会增加 token 与时延，所以只对大改动／高风险启用。
- 评审是判断型工作，结论基于证据但仍可能有盲区——它帮你把关，不替代你自己的最终决定。


`SKILL.md` 是主流程，保持精简；细节放在 `references/` 里按需加载，不占用上下文。

## 常见问题

**Q：它和直接让 AI "检查一下代码"有什么区别？**
A：直接让写代码的 AI 自查，等于让它给自己打分。vibe-check 强制实际运行取证、用独立子代理对抗评审、按固定清单逐项查，并且只给大白话结论——针对的就是"既当运动员又当裁判"的问题。

**Q：我完全不懂编程，看得懂它的报告吗？**
A：能。报告先给红绿灯结论，问题都用"这对你意味着什么"的大白话写，术语带比方，正文 ≤400 字。看不懂的地方追问即可。

**Q：它会改我的代码吗？**
A：不会。它只评审、给结论和修复指令。要不要改、怎么改，由你（或你转给编码 AI）决定。

**Q：支持哪些产品？**
A：任何支持开放 Agent Skills（`SKILL.md`）格式的产品，见[安装表](#安装)。它只依赖读文件、运行代码、（可选）子代理这些通用能力。

**Q：评审要花钱吗？**
A：skill 本身不收费。评审会消耗你所用 AI 产品的正常额度；派独立子代理会多用一些，所以只对大改动启用。

## 迭代与贡献

想改进它：编辑 `vibe-check/SKILL.md` 或 `references/` 下的文件，重新复制到 skills 目录，重启会话（Qoder `/skills reload`）即可生效。欢迎提 Issue 或 PR——尤其是补充术语比方、评审清单条目、真实翻车案例。
