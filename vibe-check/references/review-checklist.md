# 评审清单

逐项过，每项＝判据＋怎么取证＋怎么对用户说。发现问题按严重度排序，最多报 5 条。

严重度定义：**高**＝会丢数据／泄露秘密／崩溃／白花钱；**中**＝功能没做到／明显难用；**低**＝小瑕疵。

## 1. 功能兑现

- 判据：用户原话要的每一件事，代码真的做到了吗？把需求拆成清单逐条对。
- 取证：重读用户原话；按清单实际操作／运行验证，别只看函数名像不像。
- 对用户说："你要的是'关掉再打开还在'，但它一刷新就全忘——相当于写在沙滩上，浪一来就没了。"

## 2. 正确性

- 判据：空输入、超长输入、奇怪字符、边界值会不会出错？错误路径有没有处理？
- 取证：用空／边界／异常输入各跑一遍；有测试先跑测试。
- 对用户说："什么都不填直接点提交，它会整个卡死——像计算器一按等号就死机。"

## 3. 安全底线

- 判据：密钥／密码有没有写死在代码里（尤其前端网页）？用户输入有没有被直接拼进命令／SQL／HTML？
- 取证：grep 密钥特征（key／secret／token／password）；顺着用户输入的流向读代码。
- 对用户说："密钥写在网页里，等于把家门钥匙贴在门上——谁打开网页都能拿走，用你的账号花钱。"

## 4. 数据丢失风险

- 判据：数据存在哪？关程序／刷新／断电还在吗？有没有不备份就覆盖／删除的操作？
- 取证：找数据写入的位置；刷新／重启后复查数据还在不在。
- 对用户说："数据只记在'脑子'里（内存），没写进'本子'（硬盘／数据库），程序一关就全没。"

## 5. 过度设计

- 判据：方案复杂度配得上需求吗？课程作业／个人自用却上了微服务、消息队列、多个数据库？
- 取证：对比需求规模与架构；数一数为了核心功能绕了多少层。
- 对用户说："你只是要个记账页面，它却盖了栋写字楼——以后改一个小地方都要动更多文件。"

## 6. 依赖重量

- 判据：装了多少第三方包？每个都必要吗？有没有年久失修的？以后想换方案会被绑死吗？
- 取证：读 package.json／requirements.txt 等依赖清单；逐个问"去掉它行不行"。
- 对用户说："为了一个小功能借了 30 个别人的零件——任何一个坏了，你都得等别人修。"

## 7. 可回滚性

- 判据：搞砸了能退回去吗？有 git 存档吗？这一步会不会动不可逆的东西（删原始数据／花钱）？
- 取证：看 git 状态；找删除／覆盖／付费调用的位置。
- 对用户说："这一步没有后悔药：它直接改你的原始文件，改坏了退不回去。先让它备份再动手。"
